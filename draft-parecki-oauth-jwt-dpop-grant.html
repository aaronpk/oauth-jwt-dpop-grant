OAuth 2.0 JWT Authorization Grant with DPoP Binding

Abstract

This specification defines a new OAuth 2.0 authorization grant type for exchanging a JSON Web Token (JWT) assertion that is bound to a key for an access token. To use the assertion, the client must prove possession of that key using the Demonstrating Proof of Possession (DPoP) mechanism. Unlike the JWT bearer grant, a stolen assertion cannot be used by a party that does not hold the private key.¶

1. Introduction

The JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants [RFC7523] defines the use of a JWT as an authorization grant, using the grant type urn:ietf:params:oauth:grant-type:jwt-bearer. This grant type describes the use of a JWT authorization grant as a bearer token, which is susceptible to reuse by any party that obtains one.¶

OAuth 2.0 Demonstrating Proof of Possession (DPoP) [RFC9449] defines a mechanism to bind access tokens to a specific cryptographic key. This prevents the token from being used by any party that does not have access to the private key.¶

This specification extends the proof-of-possession concept to the authorization grant itself. It defines a new grant type, urn:ietf:params:oauth:grant-type:jwt-dpop, for cases where the JWT assertion is already bound to a DPoP key. To exchange the assertion for an access token, the client must provide a DPoP proof demonstrating possession of the key to which the assertion is bound. This makes the JWT assertion a sender-constrained credential.¶

A motivating use case is the Identity Assertion JWT Authorization Grant [I-D.ietf-oauth-identity-assertion-authz-grant], in which a client obtains a JWT assertion from an identity provider, typically using Token Exchange [RFC8693], and presents it to the authorization server of a different trust domain. Binding that assertion to a DPoP key prevents it from being used by any party other than the client that requested it, and allows the resulting access token to be bound to the same key.¶

2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

2.1. Terminology

This specification uses the terminology of [RFC6749], [RFC7521], [RFC7523], and [RFC9449].¶

DPoP-bound JWT assertion:

A JWT assertion that contains a cnf claim with a jkt confirmation method member identifying the public key to which the assertion is bound.¶

3. Obtaining a DPoP-Bound JWT Assertion

This specification does not define how a client obtains a DPoP-bound JWT assertion. Any mechanism may be used, provided that the issuer of the assertion binds it to a key controlled by the client. This section describes requirements on the issuer, and one way of meeting them.¶

The issuer of a DPoP-bound JWT assertion:¶

  • MUST include a cnf claim containing a jkt confirmation method member, whose value is the JWK SHA-256 Thumbprint [RFC7638] of the client's public key, as described in Section 6.1 of [RFC9449].¶

  • SHOULD verify that the client possesses the private key corresponding to that public key before issuing the assertion.¶

  • MUST NOT include more than one jkt value, or any other confirmation method member alongside jkt.¶

When the assertion is obtained from an OAuth token endpoint, such as by Token Exchange [RFC8693], the client can demonstrate possession of the key by including a DPoP header field in that request, as defined in Section 5 of [RFC9449]. The issuer validates the DPoP proof and uses the thumbprint of the public key in the proof as the value of cnf.jkt in the issued assertion. The client then uses the same key when presenting the assertion as described in Section 4.1.¶

For example, when obtaining an Identity Assertion JWT Authorization Grant (ID-JAG) as described in [I-D.ietf-oauth-identity-assertion-authz-grant], the client includes a DPoP header field in the Token Exchange request to the identity provider, and the identity provider includes the resulting cnf.jkt value in the issued ID-JAG.¶

The following non-normative example shows the decoded claims of a DPoP-bound ID-JAG:¶

{
  "iss": "https://idp.example.com",
  "sub": "U019488227",
  "aud": "https://as.example.net",
  "client_id": "f53f191f9311af35",
  "exp": 1793400300,
  "iat": 1793400000,
  "jti": "9a8b3cb8-7a1e-4d2c-8c5e-0f3e6a2c7b1d",
  "cnf": {
    "jkt": "GXIEs4thM-cVZkW7mUs9-9R731DmI7aeeBFm4VYCMUA"
  }
}
¶

4. HTTP Parameter Bindings for Transporting Assertions

The OAuth Assertion Framework [RFC7521] defines generic HTTP parameters for transporting assertions (a.k.a. security tokens) during interactions with a token endpoint. This section defines specific parameters and treatments of those parameters for use with DPoP-bound JWT assertions.¶

4.1. Using DPoP-Bound JWT Assertions as Authorization Grants

To use a DPoP-bound JWT assertion as an authorization grant, the client makes an access token request as defined in Section 4.1 of [RFC7521] with the following specific parameter values and encodings.¶

grant_type:

REQUIRED - The value MUST be urn:ietf:params:oauth:grant-type:jwt-dpop¶

assertion:

REQUIRED - A single JWT, as defined in [RFC7519], that contains a cnf claim as described in Section 5.¶

scope:

OPTIONAL - The scope parameter may be used, as defined in Section 4.1 of [RFC7521], to indicate the requested scope.¶

Authentication of the client is optional, as described in Section 3.2.1 of [RFC6749] and consequently, the client_id is only needed when a form of client authentication that relies on the parameter is used.¶

The client MUST also include a DPoP header field as defined in Section 4 of [RFC9449], which constitutes a proof of possession for the key to which the assertion is bound.¶

The following example demonstrates an access token request with a DPoP-bound JWT assertion as an authorization grant (with extra line breaks for display purposes only). The complete request, with decoded values, is shown in Appendix A.¶

POST /token HTTP/1.1
Host: as.example.net
Content-Type: application/x-www-form-urlencoded
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7Imt0eSI6
  [...omitted for brevity...]

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Ajwt-dpop
&assertion=eyJ0eXAiOiJvYXV0aC1pZC1qYWcrand0IiwiYWxnIjoiRVMyNTYi
[...omitted for brevity...]
¶

5. JWT Format and Processing Requirements

The authorization server MUST validate the JWT according to the criteria below. Application of additional restrictions and policy are at the discretion of the authorization server.¶

  1. The authorization server MUST validate the DPoP proof in the DPoP header field as described in Section 4.3 of [RFC9449].¶

  2. The authorization server MUST validate the JWT assertion according to the processing rules in Section 3 of [RFC7523] (including Section 3.1 of [RFC7523]) and Section 4 of [I-D.ietf-oauth-rfc7523bis].¶

  3. The authorization server MUST verify that the JWT assertion contains a cnf claim as defined in [RFC7800], and that the cnf claim contains a jkt confirmation method member as defined in Section 6.1 of [RFC9449].¶

  4. The authorization server MUST verify that the public key in the jwk JOSE Header Parameter of the DPoP proof matches the key to which the JWT assertion is bound. This is done in the same way a resource server confirms that a DPoP-bound access token matches the key of a DPoP proof (check 12 in Section 4.3 of [RFC9449]), using the JWK Thumbprint confirmation method of Section 6.1 of [RFC9449]: compute the base64url-encoded JWK SHA-256 Thumbprint [RFC7638] of that public key, and compare it to the value of cnf.jkt in the assertion.¶

If the DPoP proof is missing or invalid (step 1), the authorization server MUST return an error response as described in Section 5 of [RFC9449] (invalid_dpop_proof), or Section 8 of [RFC9449] (use_dpop_nonce) if a nonce is required. If any of the remaining validation steps fail, the authorization server MUST return an invalid_grant error response.¶

5.1. DPoP Nonces and Replay

The authorization server MAY require the client to include a nonce in the DPoP proof, as described in Section 8 of [RFC9449]. In that case the authorization server responds to a request without a valid nonce with a use_dpop_nonce error and a DPoP-Nonce header field, and the client retries the request with a new DPoP proof containing the provided nonce and the same assertion.¶

The authorization server SHOULD perform replay detection on the jti claim of the DPoP proof, as described in Section 11.1 of [RFC9449]. The authorization server MAY also reject assertions whose jti has already been used, as described in Section 3 of [RFC7523].¶

If the authorization server records assertion jti values to detect replay, it MUST NOT record the assertion's jti as used when the request is rejected because of an invalid or missing DPoP proof or nonce. Otherwise a client following the nonce retry described above would have its assertion rejected as a replay. Performing the validation steps in the order given in Section 5 achieves this.¶

5.2. Use with the JWT Bearer Grant Type

An authorization server that supports the grant type defined in this specification MUST NOT accept a DPoP-bound JWT assertion as an authorization grant using the urn:ietf:params:oauth:grant-type:jwt-bearer grant type defined in [RFC7523], and MUST return an invalid_grant error response if one is presented. This applies whether or not the request includes a DPoP header field.¶

An authorization server that supports this specification SHOULD include urn:ietf:params:oauth:grant-type:jwt-dpop in the grant_types_supported value of its authorization server metadata [RFC8414].¶

6. Access Token Response

If the request is valid, the authorization server issues an access token. The issued access token SHOULD be DPoP-bound to the key from the DPoP proof, which is the same key to which the assertion is bound. In this case the token_type in the response MUST be DPoP, as described in Section 5 of [RFC9449].¶

The authorization server MAY instead issue a bearer access token, for example when the protected resources for which the token is intended do not support DPoP. In this case the token_type MUST be Bearer. See Section 7.2 for the security implications.¶

If the authorization server issues a refresh token, the refresh token is subject to the binding requirements of Section 5 of [RFC9449]: a refresh token issued to a public client MUST be bound to the key from the DPoP proof. The authorization server SHOULD NOT issue a refresh token whose lifetime extends beyond what is permitted by the policy under which the assertion was issued.¶

7. Security Considerations

The security considerations described within the following specifications are all applicable to this document: "Assertion Framework for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7521], "JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7523], "Updates to OAuth 2.0 JSON Web Token (JWT) Client Authentication and Assertion-Based Authorization Grants" [I-D.ietf-oauth-rfc7523bis], "OAuth 2.0 Demonstrating Proof of Possession (DPoP)" [RFC9449], "The OAuth 2.0 Authorization Framework" [RFC6749], and "JSON Web Token (JWT)" [RFC7519].¶

7.1. Downgrade to the JWT Bearer Grant

The binding of a DPoP-bound JWT assertion only provides protection if the authorization server enforces it. An attacker that obtains a DPoP-bound JWT assertion, but not the corresponding private key, could present the assertion using the urn:ietf:params:oauth:grant-type:jwt-bearer grant type instead of the grant type defined in this specification. An authorization server that processes the assertion only according to [RFC7523] would ignore the cnf claim and issue an access token, defeating the binding entirely.¶

Authorization servers that support this specification prevent this attack by rejecting DPoP-bound JWT assertions presented with the jwt-bearer grant type, as required by Section 5.2.¶

Authorization servers that do not implement this specification are not aware of this requirement and may accept a DPoP-bound JWT assertion as a bearer assertion. For this reason, an issuer of DPoP-bound JWT assertions SHOULD NOT issue one for use at an authorization server unless it knows that the authorization server supports this specification, for example because the authorization server advertises urn:ietf:params:oauth:grant-type:jwt-dpop in its grant_types_supported metadata [RFC8414], or by prior configuration.¶

7.2. Issuing Bearer Access Tokens

When the authorization server issues a bearer access token in response to this grant, the DPoP binding no longer protects the access token. The assertion cannot be used by a party that does not hold the private key, but the resulting access token can be used by any party that obtains it. Authorization servers SHOULD issue DPoP-bound access tokens whenever the intended protected resources support them.¶

Even when a bearer access token is issued, a refresh token issued to a public client is still bound to the DPoP key, as described in Section 5 of [RFC9449]. As noted there, binding only the refresh token can improve the security posture even when protected resources do not support DPoP, since a stolen refresh token cannot be used to obtain new access tokens without the private key.¶

8. Privacy Considerations

The jkt value in a DPoP-bound JWT assertion is a stable identifier of the client's key. When a client uses the same key with an identity provider, with one or more authorization servers, and with the protected resources to which DPoP-bound access tokens are presented, each of these parties observes the same key, either in DPoP proofs or as cnf.jkt in assertions and access tokens. Colluding parties could use this to correlate the client's activity across them, beyond what is already possible from the identity of the client or the user.¶

To limit this, a client MAY use a different DPoP key for each authorization server at which it presents DPoP-bound JWT assertions. Since the assertion is bound to the key used when requesting it (see Section 3), the client needs to choose the key it will use at the target authorization server before requesting the assertion. A client SHOULD NOT reuse a DPoP key across unrelated users or sessions where doing so would let those otherwise unlinked activities be correlated.¶

This specification does not change the claims about the user that are conveyed in the assertion, and the privacy considerations of the specification defining the assertion, such as [I-D.ietf-oauth-identity-assertion-authz-grant], continue to apply.¶
